# Performance experiments

This file lists the performance ideas that we tried in minimenta, what happened, and the evidence. It has two goals. Nobody should repeat an idea that we already dropped. Every result must have a source that anyone can open.

The log covers [#1](https://github.com/OriginalMHV/minimenta/pull/1) (merged on 2026-10-07) to [#36](https://github.com/OriginalMHV/minimenta/pull/36) (merged on 2026-10-09), and it covers [#42](https://github.com/OriginalMHV/minimenta/pull/42) (merged on 2026-10-10). It is current to main at [`5e775fc`](https://github.com/OriginalMHV/minimenta/commit/5e775fc) ([#37](https://github.com/OriginalMHV/minimenta/pull/37)). The PRs [#38](https://github.com/OriginalMHV/minimenta/pull/38) to [#41](https://github.com/OriginalMHV/minimenta/pull/41) change the user interface and have no row. Most experiment branches are deleted. One stays on GitHub on 2026-10-09: [`perf/windows-hybrid-mft`](https://github.com/OriginalMHV/minimenta/tree/perf/windows-hybrid-mft) (head [`d5a5f67`](https://github.com/OriginalMHV/minimenta/commit/d5a5f67)), the closed [#34](https://github.com/OriginalMHV/minimenta/pull/34). The branch of the Linux scheduler study (`experiment/linux-sched-build`, head [`8a48db1`](https://github.com/OriginalMHV/minimenta/commit/8a48db1)) was deleted after its last run, like the branch of the Linux disk floor study. The branch of the fix round for the review of [#42](https://github.com/OriginalMHV/minimenta/pull/42) (`experiment/linux-sched-fix42`, head [`3acf6de`](https://github.com/OriginalMHV/minimenta/commit/3acf6de)) was deleted after its last run, too. The head [`135cbde`](https://github.com/OriginalMHV/minimenta/commit/135cbde) of the disk floor branch still resolves by hash. The runs and commits of the deleted branches stay on GitHub too, and each row links to them. Rows are in time order, because PR numbers and run IDs rise with time.

Each row has one status word:

| Status | Meaning |
| --- | --- |
| Kept | The change is on main, or we use the practice today. |
| Dropped | We tried the idea and did not keep it. The row says why. |
| Open | We found a problem or a gap and have no fix. |
| In progress | Work on it is running now. |
| Superseded | A later change replaced it. The row names that change. |

A status word with an open pull request in brackets, for example Kept (#N, open), means that the change is in that pull request and not on main yet. We change the word when the pull request merges.

Ideas that nobody has tried are in [Not tried yet](#not-tried-yet).

## How we measure

Read this section before you compare two numbers. The scripts are in [bench/](../bench/). The [Speed workflow](../.github/workflows/speed.yml) runs them against ncdu, gdu, dua-cli and dust.

- **Interleaved pairs.** [bench/interleave.py](../bench/interleave.py) runs two commands in alternating pairs and swaps the order in every pair. It reports the median of the pair ratios, the middle half (25th to 75th percentile) and the number of pairs. We changed to this method because separate hyperfine series gave 1.01x to 1.74x for almost the same code ([run 37687942332](https://github.com/OriginalMHV/minimenta/actions/runs/37687942332), [run 37688756750](https://github.com/OriginalMHV/minimenta/actions/runs/37688756750), [run 37689273806](https://github.com/OriginalMHV/minimenta/actions/runs/37689273806), [run 37689680186](https://github.com/OriginalMHV/minimenta/actions/runs/37689680186)). The first interleaved run gave 1.76x (middle half 1.68x to 1.80x, 60 pairs, [run 37690716325](https://github.com/OriginalMHV/minimenta/actions/runs/37690716325), [`3d78440`](https://github.com/OriginalMHV/minimenta/commit/3d78440)).
- **How to read a ratio.** A ratio is the time of the other command divided by the time of the command under test. Above 1 means that the command under test is faster. The Result cells use the words "faster" and "slower" and give times where we have them. "Even" means that the middle half of the pair ratios includes 1.0 ([README](../README.md#speed)).
- **Cold means the file cache is dropped before every run.** Linux: `sync`, then `echo 3 > /proc/sys/vm/drop_caches` ([bench/cold.sh](../bench/cold.sh)). macOS: `sync`, then `sudo purge` (also bench/cold.sh). Windows: empty the working sets and purge the standby list ([bench/windows-purge.ps1](../bench/windows-purge.ps1), and an in-process copy in [bench/compare.py](../bench/compare.py)). Warm means that the cache already holds the tree.
- **The cloud host may still cache the disk.** Dropping the cache clears the guest only. The first scan of `/usr` on a fresh Linux runner took minimenta 61.6 s ([run 37899170123](https://github.com/OriginalMHV/minimenta/actions/runs/37899170123)). Cold scans after a cache drop took a median of 7.9 s ([run 37904223270](https://github.com/OriginalMHV/minimenta/actions/runs/37904223270)). So a cold number describes a disk behind a host cache. We did not time the other tools on a true first read.
- **Runners differ between runs.** Seven Speed runs used five Linux CPU types ([run 37901931836](https://github.com/OriginalMHV/minimenta/actions/runs/37901931836), [run 37904223270](https://github.com/OriginalMHV/minimenta/actions/runs/37904223270), [run 37909487571](https://github.com/OriginalMHV/minimenta/actions/runs/37909487571), [run 37925163523](https://github.com/OriginalMHV/minimenta/actions/runs/37925163523), [run 37934913055](https://github.com/OriginalMHV/minimenta/actions/runs/37934913055), [run 37934917329](https://github.com/OriginalMHV/minimenta/actions/runs/37934917329), [run 37934922096](https://github.com/OriginalMHV/minimenta/actions/runs/37934922096)). The ratio of ncdu with its defaults on cold `/usr` was 3.30x, 4.41x, 5.59x, 3.93x, 4.48x, 4.02x and 3.03x. Compare ratios inside one run. Read each ratio as one sample on one machine type.
- **Few cold pairs.** Cold runs are long, so many rows have 2 to 8 pairs. The middle half is then wide. For example, 3 pairs gave 0.79x to 1.01x ([run 37758061611](https://github.com/OriginalMHV/minimenta/actions/runs/37758061611)).
- **Trees.** The warm tree is the synthetic tree from [bench/gen_tree.py](../bench/gen_tree.py), with 51,110 items and 1,111 directories ([#4](https://github.com/OriginalMHV/minimenta/pull/4)). The cold trees are `/usr` on Linux, `/opt/homebrew` and `/System/Library` on macOS, and `C:\Program Files` on Windows ([README](../README.md#speed)).
- **Experiment method.** An experiment runs on a branch named `experiment/<name>` with its own workflow job. Most jobs build main and the variant in the same job and compare them in interleaved pairs. The helper scripts and variant code of the Linux experiments are not on main. They exist only in the commits that the rows cite: [`d3a0e79`](https://github.com/OriginalMHV/minimenta/commit/d3a0e79) (`bench/coldio_linux.py`), [`a7a785a`](https://github.com/OriginalMHV/minimenta/commit/a7a785a) (`bench/walk_linux.c`), [`7a1c21f`](https://github.com/OriginalMHV/minimenta/commit/7a1c21f) and [`e8d3b2d`](https://github.com/OriginalMHV/minimenta/commit/e8d3b2d) (`bench/replica_linux.py`), [`1357fad`](https://github.com/OriginalMHV/minimenta/commit/1357fad) (`bench/firsttouch_linux.py`), [`75e39d8`](https://github.com/OriginalMHV/minimenta/commit/75e39d8) (`bench/rusage_linux.py`), [`135cbde`](https://github.com/OriginalMHV/minimenta/commit/135cbde) (`bench/floor/`, the disk floor study), [`3acf6de`](https://github.com/OriginalMHV/minimenta/commit/3acf6de) (`bench/sched/`, the fix round of [#42](https://github.com/OriginalMHV/minimenta/pull/42)). The macOS probe `bench/cold_probe.c` is in [`318079d`](https://github.com/OriginalMHV/minimenta/commit/318079d).
- **Simulated fast disk.** The Azure runner kernel has no `null_blk` module, even with `linux-modules-extra` ([run 37850917065](https://github.com/OriginalMHV/minimenta/actions/runs/37850917065) ran the `null_blk` setup of [`7a1c21f`](https://github.com/OriginalMHV/minimenta/commit/7a1c21f) and failed). It does load `scsi_debug` ([run 37851633830](https://github.com/OriginalMHV/minimenta/actions/runs/37851633830)). We use `scsi_debug` with 100 us per request for a fast device (`modprobe scsi_debug dev_size_mb=3072 ndelay=100000` in [`1357fad`](https://github.com/OriginalMHV/minimenta/commit/1357fad) and [`e8d3b2d`](https://github.com/OriginalMHV/minimenta/commit/e8d3b2d)).

**Notes**

- **Thread count.** A cold scan waits for the disk and the kernel, so more reads in flight help. On the Linux runner, 16 threads kept 14.5 reads in flight at 0.97 ms each, and 64 threads kept 60.5 in flight at 4.09 ms each. The wall time was the same (7.83 and 7.93 s, [run 37849838228](https://github.com/OriginalMHV/minimenta/actions/runs/37849838228)). A warm scan pays for each extra thread: 35.4 ms with 32 threads against 33.0 ms with 4 ([run 37761199192](https://github.com/OriginalMHV/minimenta/actions/runs/37761199192)). On a simulated device with 100 us per request, 4 threads took 4.64 s and 16 threads took 1.96 s ([run 37852061499](https://github.com/OriginalMHV/minimenta/actions/runs/37852061499)).
- **Local Mac.** A hand check on a local Mac found 16 threads 1.05x faster than one thread per core (warm, 8 pairs). It has no run ([#7](https://github.com/OriginalMHV/minimenta/pull/7)). The same PR withdraws an earlier local sweep that said more threads than cores slow macOS. That sweep used a tiny tree and a noisy machine.
- **Sort at the root.** The browser already sorts a directory when it opens it, and ncdu also sorts only for display ([#4](https://github.com/OriginalMHV/minimenta/pull/4)).
- **Small tree after mimalloc.** The warm small tree ratio against `ncdu -t 4` on main CI had a median of about 1.05x in the 8 runs before [#14](https://github.com/OriginalMHV/minimenta/pull/14) (range 1.02x to 1.10x). It had a median of about 0.94x in the 20 runs after it (range 0.88x to 1.04x). The one-thread ratio stayed between 1.04x and 1.12x. [#19](https://github.com/OriginalMHV/minimenta/pull/19) says 12 runs before the change. We count 8 CI runs on main with the Linux benchmark job.
- **Start cost.** Process start took 1.09 ms with mimalloc and 0.71 ms with the system allocator. An empty directory with 16 threads took 2.78 ms against 1.70 ms. ncdu needs 0.27 ms and 0.45 ms ([run 37854970267](https://github.com/OriginalMHV/minimenta/actions/runs/37854970267)).
- **Chart runs.** All three runs measured main at [`b1c0edd`](https://github.com/OriginalMHV/minimenta/commit/b1c0edd) on 2026-10-09. The first ran on main. The other two ran on the temporary refs `speed/run-b` and `speed/run-c`, which are deleted. The runner CPU changed between runs. Windows had AMD Family 26, 25 and 25 CPUs. Linux had EPYC 9V74, EPYC 9V45 and Xeon 8573C CPUs ([#36](https://github.com/OriginalMHV/minimenta/pull/36)).

- **Why Linux has no big win.** One `fstatat` per entry costs about 1.4 us on the runner and is about 75% of a warm scan ([#4](https://github.com/OriginalMHV/minimenta/pull/4)). Linux has no bulk stat call for a normal user. A perf profile puts 94% of the samples in the kernel and under 2% in minimenta ([#4](https://github.com/OriginalMHV/minimenta/pull/4), [run 37739711119](https://github.com/OriginalMHV/minimenta/actions/runs/37739711119)). The warm syscall floor was 29.7 ms with 4 threads and 100.1 ms with 1 thread. In the same run, minimenta took 32.7 and 107.0 ms and ncdu took 34.8 and 110.3 ms ([run 37741994766](https://github.com/OriginalMHV/minimenta/actions/runs/37741994766)). The [#4](https://github.com/OriginalMHV/minimenta/pull/4) text quotes a floor of 30.1 and 99.6 ms from another run.
- **Why a cold scan is slow.** Every tool and variant made 117,312 to 117,454 block reads on cold `/usr` ([run 37849838228](https://github.com/OriginalMHV/minimenta/actions/runs/37849838228)). Both 16 and 64 threads reach about 15,000 reads per second. The read count is nearly fixed, so the device or the host cache sets the time. In a 64-thread profile, `getdents64` alone took 10.26 to 10.30 s and adding `fstatat` took 10.36 to 10.47 s, so the stats add about 1% when cold. A real scan took 8.2 s ([#10](https://github.com/OriginalMHV/minimenta/pull/10), [run 37780736716](https://github.com/OriginalMHV/minimenta/actions/runs/37780736716), [run 37779251864](https://github.com/OriginalMHV/minimenta/actions/runs/37779251864)). A later replay with a known directory list shows that the read order changes the read count by only 1% to 2% and the time by much more (see the Open row on random order). [#42](https://github.com/OriginalMHV/minimenta/pull/42) applies it.
- **Simulated fast disk.** The device is `scsi_debug` with 100 us per request and an ext4 copy of `/usr` (109,419 directories). Medians of 4: minimenta took 1.96 s with 16 threads, 1.94 s with 64 threads and 4.64 s with 4 threads. ncdu took 2.01 s with 16 threads and 1.97 s with 64 threads ([run 37852061499](https://github.com/OriginalMHV/minimenta/actions/runs/37852061499)). Against main, the large directory change was 1.01x on this device ([run 37854877327](https://github.com/OriginalMHV/minimenta/actions/runs/37854877327)).
- **Host cache.** On untouched trees read once, the four tools read only 1,200 to 4,100 blocks per second on each of four runners. Pooled over the runners, minimenta with 16 threads read 1,915, with 64 threads 1,727, ncdu with 16 threads 1,902 and with 64 threads 1,790 ([run 37852061499](https://github.com/OriginalMHV/minimenta/actions/runs/37852061499)). A direct `fio` test of the raw root device gave 89 reads per second at queue depth 1 and 1,244 at depth 64 ([run 37849838228](https://github.com/OriginalMHV/minimenta/actions/runs/37849838228)). This is why we do not call the cold runs "raw disk" runs.
- **Large directories.** The first 64 KiB batch is statted on the listing thread, so normal directories create no task. ncdu has the same limit as the old minimenta code: `ncdu -t 4` took 480 ms on the same directory ([run 37854877327](https://github.com/OriginalMHV/minimenta/actions/runs/37854877327)). No run covers directories with 2 to 10 batches, and no run measured peak memory. [#30](https://github.com/OriginalMHV/minimenta/pull/30) added a cancel check and a cap of 4 queued batches per thread. It makes no speed claim. Without the cap, 5 million long names could queue about 1.4 GB. That is a calculation in [#30](https://github.com/OriginalMHV/minimenta/pull/30), not a measurement.

The saving does not show on 51k items. A second run gave 4% faster with a middle half of 0.99x to 1.12x ([run 37856183360](https://github.com/OriginalMHV/minimenta/actions/runs/37856183360)).

**Notes**

- **Where macOS stands.** In [run 37904223270](https://github.com/OriginalMHV/minimenta/actions/runs/37904223270) (cold, 15 and 11 pairs), `/opt/homebrew` (200,140 items) took minimenta 1.04 s. ncdu with its defaults was 4.43x slower and `ncdu -t 64` was 1.67x slower. `/System/Library` (427,459 items): 4.53x and 1.96x. On `/System/Library` the other tools open every folder and minimenta skips the empty ones, so that tree favors minimenta. The ratios against `ncdu -t 64` in the four Speed runs were 1.67x to 2.09x. In the three runs of [#36](https://github.com/OriginalMHV/minimenta/pull/36) they were 1.78x to 2.05x on `/opt/homebrew`. minimenta did not reach 2x in every run.
- **Why a macOS scan is kernel bound.** Cold `/System/Library` (144,916 directories) took 3.8 to 4.4 s with 16 to 64 threads. The system CPU time was 8.3 to 9.7 s with 8 to 64 threads. A C probe with the same calls was no faster. On one thread, each open took 17 to 20 us and each listing took 35 to 47 us. With 16 threads, all 16 were inside `read_dir` in 84.6% and 87.7% of the samples ([run 37849524892](https://github.com/OriginalMHV/minimenta/actions/runs/37849524892), [run 37852547064](https://github.com/OriginalMHV/minimenta/actions/runs/37852547064)). So better scheduling cannot help, and fewer opens can. This led to [#23](https://github.com/OriginalMHV/minimenta/pull/23).
- **The cache rules.** Two adversarial reviews changed the cache. A subtree is now reused only when the name and the directory inode match, not by name alone ([`1250b13`](https://github.com/OriginalMHV/minimenta/commit/1250b13), [`b5827a5`](https://github.com/OriginalMHV/minimenta/commit/b5827a5)). Mounted volumes ask for their own FSEvents history, because a probe showed that the stream of the root has no events for other volumes ([`fabde6e`](https://github.com/OriginalMHV/minimenta/commit/fabde6e), probe: internal notes). Esc cancels the replay, and a cache older than 7 days is ignored. A known limit remains: a directory renamed away, changed and renamed back keeps its cached contents until a full scan ([#3](https://github.com/OriginalMHV/minimenta/pull/3)).
- **Noise on the runner.** Run 37853794004 showed the warm 51k tree at 0.66x (middle half 0.50x to 1.19x, 40 pairs). A recheck with 100 pairs gave 1.03x and 0.96x ([run 37854822714](https://github.com/OriginalMHV/minimenta/actions/runs/37854822714)). The 0.66x was runner noise.
- **Repeat scans.** The gains of [#20](https://github.com/OriginalMHV/minimenta/pull/20) and [#21](https://github.com/OriginalMHV/minimenta/pull/21) are best cases, because the cache was written seconds earlier. The Xcode.app row of [#20](https://github.com/OriginalMHV/minimenta/pull/20) (1.06x, middle half 1.00x to 1.16x, [run 37851225477](https://github.com/OriginalMHV/minimenta/actions/runs/37851225477)) is noise-sized. Cached totals matched a fresh scan in the runs of [#21](https://github.com/OriginalMHV/minimenta/pull/21) ([run 37853202229](https://github.com/OriginalMHV/minimenta/actions/runs/37853202229), [run 37853798602](https://github.com/OriginalMHV/minimenta/actions/runs/37853798602)).

- **Start gate and threads.** Cold, the gate against no gate took 4.18 against 4.03 s (5 pairs), which is inside noise ([run 37842754606](https://github.com/OriginalMHV/minimenta/actions/runs/37842754606)). The cost of 64 scan threads was a warm empty folder 1.34x slower (18.1 against 13.6 ms), a warm 51k tree 1.16x slower (41.3 against 35.6 ms) and a cold administrator scan 1.30x slower ([run 37851294362](https://github.com/OriginalMHV/minimenta/actions/runs/37851294362)).
- **Why [#34](https://github.com/OriginalMHV/minimenta/pull/34) was closed.** Main starts the reader early and takes 1.8x to 3.2x as long as the listing alone on folders that list in about 1 to 2 s (see the Open row and the race cost note above). [#34](https://github.com/OriginalMHV/minimenta/pull/34) starts it after 3 s. The closing [comment on #34](https://github.com/OriginalMHV/minimenta/pull/34#issuecomment-6081533783) says that this loses 1.7x to 1.8x on folders of 85k items or more (`C:\Program Files` 6.80 against 3.98 s, a 100k-item Visual Studio folder 6.79 against 3.88 s). The same comment says that no early signal can choose between the two policies, because the depth-first listing has only walked the start of each tree at 0.65 s. It also says that the owner decided beforehand to keep main if the predictor failed. A second hybrid run showed the same direction ([run 37912086364](https://github.com/OriginalMHV/minimenta/actions/runs/37912086364)). The predictor was tested offline, not in A/B runs ([comment on #34](https://github.com/OriginalMHV/minimenta/pull/34#issuecomment-6081533783)). The first hybrid run ([run 37905006616](https://github.com/OriginalMHV/minimenta/actions/runs/37905006616)) is not used, because both builds shared one target directory.
- **Defender.** The runners have Defender real-time monitoring off. We did not measure Windows with Defender on. The README says that endpoint security software slows the directory opens of every tool and narrows the gap to ncdu.
- **Correctness gaps.** The listing counts each hard link and the MFT counts a hard-linked file once ([#13](https://github.com/OriginalMHV/minimenta/pull/13)). The `-x` option has no effect on Windows, because mount points are reparse points ([#12](https://github.com/OriginalMHV/minimenta/pull/12)).

## Measurement mistakes we made

Each item cost us time or produced a wrong claim. Check for them in new work.

1. **Host cache below the VM.** A cold CI number is not a true first read. The first scan of `/usr` on a fresh runner took 61.6 s and 62.6 s in two runs. A cold scan after `drop_caches` took 7.7 to 7.9 s, which is about 8x less ([run 37899170123](https://github.com/OriginalMHV/minimenta/actions/runs/37899170123), [run 37852460511](https://github.com/OriginalMHV/minimenta/actions/runs/37852460511)). On the raw disk, `fio` read the slowest 1 GiB window at 555 to 682 IOPS on first touch and at 19,351 to 19,753 IOPS after one sequential read of it ([run 37958667349](https://github.com/OriginalMHV/minimenta/actions/runs/37958667349)).
2. **Timer steps of 50 ms.** In the first Speed run, 61 of 63 warm Linux tool times were 64, 65, 66, 114, 115, 164 or 165 ms. Python `Popen.wait(timeout)` polls with a sleep that grows to 50 ms, so a short command is noticed late. That inflated the ratios of the other tools. [`f7a86bd`](https://github.com/OriginalMHV/minimenta/commit/f7a86bd) waits without a timeout and kills a long command from a timer thread. In run 37904223270, 7 of 420 warm Linux tool times sit on those values (macOS: 15 of 420, Windows: 0 of 240) ([run 37900157486](https://github.com/OriginalMHV/minimenta/actions/runs/37900157486), [run 37904223270](https://github.com/OriginalMHV/minimenta/actions/runs/37904223270)).
3. **Cargo reused one binary.** An A/B job built main and the branch into one target directory. The branch build finished in 0.14 s after the main build took 49.90 s, so both variants were main. The run is discarded ([run 37905006616](https://github.com/OriginalMHV/minimenta/actions/runs/37905006616)). The fix builds the binaries in separate directories and fails when the branch binary has no trace line ([run 37908579496](https://github.com/OriginalMHV/minimenta/actions/runs/37908579496)).
4. **Runner CPU variance.** The same code gave an MFT scan of 8.1 s on one runner and 4.1 s on another ([run 37901931836](https://github.com/OriginalMHV/minimenta/actions/runs/37901931836), [run 37904223270](https://github.com/OriginalMHV/minimenta/actions/runs/37904223270)). Windows jobs in one run got three CPU models ([run 37926570626](https://github.com/OriginalMHV/minimenta/actions/runs/37926570626)). Compare ratios inside one run.
5. **The first round on a fresh VM is slow.** In round 1 on `C:\Program Files\Amazon`, three variants took 5.97, 5.35 and 5.00 s, while their medians were 1.94, 1.88 and 1.97 s. The first `--no-mft` round on `C:\Program Files` took 32.84 s against a median of 14.24 s ([run 37908579496](https://github.com/OriginalMHV/minimenta/actions/runs/37908579496)). Keep the first round in the log, mark it, and take medians from later rounds.
6. **Separate series.** Separate hyperfine series gave 1.01x to 1.74x for almost the same code. See [How we measure](#how-we-measure).
7. **Too few cold pairs.** Three pairs gave `ncdu -t 64` as 0.97x with a middle half of 0.79x to 1.01x ([run 37758061611](https://github.com/OriginalMHV/minimenta/actions/runs/37758061611)). Eight pairs made us write "ncdu about 5% faster" in [#11](https://github.com/OriginalMHV/minimenta/pull/11). Seven pairs later gave 0.979x, which is even ([run 37904223270](https://github.com/OriginalMHV/minimenta/actions/runs/37904223270)). Make a claim only after several runs.
8. **One noisy A/B.** A warm run showed 0.66x for a change that had no effect. Another run with 100 pairs gave 1.03x ([run 37853794004](https://github.com/OriginalMHV/minimenta/actions/runs/37853794004), [run 37854822714](https://github.com/OriginalMHV/minimenta/actions/runs/37854822714)).
9. **Large trees only.** [#14](https://github.com/OriginalMHV/minimenta/pull/14) measured only large trees, so it missed the small tree loss that the main CI series showed later ([#19](https://github.com/OriginalMHV/minimenta/pull/19)).
10. **Tiny trees for thread sweeps.** A sweep on the 51k tree suggested that more threads than cores slow macOS. Sweeps on a large tree showed the opposite ([run 37690300843](https://github.com/OriginalMHV/minimenta/actions/runs/37690300843), [run 37768890821](https://github.com/OriginalMHV/minimenta/actions/runs/37768890821)).
11. **Numbers copied from notes.** "io_uring is about 2x slower" had no run behind it. The worst measured case is 1.68x at 4 threads ([run 37747203134](https://github.com/OriginalMHV/minimenta/actions/runs/37747203134)). The [#4](https://github.com/OriginalMHV/minimenta/pull/4) text quotes the syscall floor of one run next to the times of another run ([run 37741994766](https://github.com/OriginalMHV/minimenta/actions/runs/37741994766)). The label "ncdu -t 64 (its fastest cold setting)" in [bench/cold.sh](../bench/cold.sh) is not proven, because we compared only -t 4, 16 and 64 (21.7 s, 11.7 s and 7.8 s, [run 37758061611](https://github.com/OriginalMHV/minimenta/actions/runs/37758061611)). Re-read the log for every number.
12. **Median of ratios is not the ratio of medians.** For the Windows `--no-mft` row of run 37904223270, 13.54 s over 4.05 s is 3.34, but the median of the pair ratios is 3.351 ([run 37904223270](https://github.com/OriginalMHV/minimenta/actions/runs/37904223270)). The README makes the same point for the three runs of [#36](https://github.com/OriginalMHV/minimenta/pull/36): 13.60 s over 4.00 s is 3.40, and the ratio is 3.455 ([README](../README.md#speed)).
13. **A detector built on single reads.** The `hybrid` scheduler timed each directory read. It fired in every warm scan, because a read that the scheduler pauses looks slow. We saw it only because the warm runs printed the pool size. Test a detector on the case where it must stay silent, on a machine as busy as in the run ([run 37966442656](https://github.com/OriginalMHV/minimenta/actions/runs/37966442656), [`557ecd5`](https://github.com/OriginalMHV/minimenta/commit/557ecd5)).
14. **A single job has no margin.** One noisy VM gave 1.085 for the new scheduler, and the A/A control (main against main) gave 1.088 in the same job. Run the same binary twice in every job and read that ratio before a verdict ([run 37977331383](https://github.com/OriginalMHV/minimenta/actions/runs/37977331383)).
15. **A smoke run is not a measurement.** A smoke run with one cold round per job gave 1.21x for a folder with 30,000 subfolders in all 6 jobs ([run 37985467193](https://github.com/OriginalMHV/minimenta/actions/runs/37985467193)). The first cold round of run C repeated it (median 1.25x, [run 37990844034](https://github.com/OriginalMHV/minimenta/actions/runs/37990844034)), and rounds 1 to 5 pooled gave 0.997. All six rounds pooled gave 1.000, so the pooled median hides the first scan. The first scan of a round after a tree is built probably reads from a warmer host cache. We did not test that. Use a smoke run to test the harness only.
16. **A memory estimate from the structs.** The review of [#42](https://github.com/OriginalMHV/minimenta/pull/42) estimated 150 to 250 MB more memory for 1 million subfolders. We measured 16 to 22 MB more for 520,000 subfolders ([run 37986765908](https://github.com/OriginalMHV/minimenta/actions/runs/37986765908), [run 37990715838](https://github.com/OriginalMHV/minimenta/actions/runs/37990715838)). Measure before you write a number.
17. **Runs that overlap are one batch.** Two runs pushed 7 seconds apart ran at the same time and are not two replicates in time ([run 37977331383](https://github.com/OriginalMHV/minimenta/actions/runs/37977331383), [run 37977344668](https://github.com/OriginalMHV/minimenta/actions/runs/37977344668)). Start the second run after the first has ended.
18. **A code path that no run reaches.** A full pool left the refused subfolders to one thread. No benchmark filled the pool, and the unit test checked only the tree. A review found it by reading the code. A switch that forces the pool on measured it on 520,000 subfolders. The median of 24 cold scans over [run 37986765908](https://github.com/OriginalMHV/minimenta/actions/runs/37986765908) and [run 37990715838](https://github.com/OriginalMHV/minimenta/actions/runs/37990715838) was 2.5x slower. The two runs alone gave 2.9x and 2.3x. Force every rare path in a run.

## Not tried yet

These ideas came up in research or review and nobody has measured them. "Internal notes" means research or review notes that are not public. We list them so that nobody thinks they are new, and so that nobody thinks they were tried.

**All platforms**

- Time-to-top-10: log when the final 10 largest files and folders are first known during a scan, on three cold real trees with at least 7 interleaved pairs each. Build a live "largest so far" list only if the median is below about 30% to 50% of the scan time. Source: internal notes.
- Stop-and-keep: a second key ends the scan and keeps the partial tree, flagged as incomplete. Source: internal notes.
- Show the last saved tree at once and refresh it in the background, on Linux, Windows, and on macOS when the FSEvents replay cannot be used. Needs delete disabled while the tree is stale. Source: internal notes.
- Measure on real hardware: a local NVMe disk, a rotating disk, an aged ext4 volume, XFS and btrfs. All cold numbers so far come from Azure virtual disks, `scsi_debug` and a virtual Mac. Source: internal notes.
- Time ncdu, gdu, dua-cli and dust on a true first read. The README says we did not ([run 37899170123](https://github.com/OriginalMHV/minimenta/actions/runs/37899170123)).
- Find the root cause of the mimalloc small tree loss and the tree size where mimalloc starts to win. Only 51,110 items and 304,060 to 737,881 items were measured.

**Linux**

- Read directories in physical order inside the scanner, with the `FIEMAP` block of each child directory as the key of one shared frontier. The replay with a known list showed no gain over inode order for a shared queue (see the Dropped row above). It showed a gain for one slice per thread (8.09 to 9.40 s against 8.97 to 10.34 s for readdir order at 64 threads, see the Open row on slices). The scanner version was never built.
- Prefetch the ext4 directory blocks from the block device inside minimenta. Only a probe ran (see the Open row above). The probe needs read access to the block device and a block list from an earlier census. Three internal reviewers judged the idea not viable for a normal user. Source: internal notes.
- A direct ext4 metadata reader raced against the walk, for root only. Plan: a one-day read-only spike, and a go only at 1.3x or better. The owner has not decided. The prefetch probe above is the nearest data. Source: internal notes.
- `XFS_IOC_BULKSTAT` priming and btrfs `TREE_SEARCH_V2`. Both need `CAP_SYS_ADMIN` and do nothing on ext4. Source: internal notes.
- `O_NOATIME` on directory opens, with a fallback on `EPERM`. Check the write rate during one cold scan first. Source: internal notes.
- Parallel `getdents64` of one huge ext4 directory by hash range. [#26](https://github.com/OriginalMHV/minimenta/pull/26) parallelizes only the stats.
- Detect a rotating disk and use fewer threads. The idea comes from a third-party tool. No hard disk was measured.
- Add disk-read counters and a throttled disk (cgroup `io.max`) to the Linux benchmark job, so the host cache effect shows in every run.
- Benchmark the large directory path on mid-size directories (for example 200 directories of 3,000 to 10,000 files). Also measure peak memory, and `-t 1` and `-t 2`, for the 200,000-file directory. No run covers them.
- Reduce the small tree gap to `ncdu -t 4` (about 3.6 ms of 36 ms). Options: lazy thread creation, an allocator choice by tree size, other mimalloc settings. See [run 37854970267](https://github.com/OriginalMHV/minimenta/actions/runs/37854970267).
- Test the 1 KiB `getdents64` buffer of ncdu alone. It was tested only inside the ncdu-like C probe ([run 37850682435](https://github.com/OriginalMHV/minimenta/actions/runs/37850682435)).
- Level-synchronous sorted frontier or another global order. The simple LIFO and FIFO probes lost ([run 37850682435](https://github.com/OriginalMHV/minimenta/actions/runs/37850682435)), `fr-lifo` lost too, and the random pool won ([#42](https://github.com/OriginalMHV/minimenta/pull/42)). Sorted variants are untried. Source: internal notes.
- Check the spread scheduler on a machine with 16 or more cores. The hosted runners of this account have 4 vCPUs, so the limits of the detector were never tested on more.
- Check the spread scheduler on a rotating disk, on an NFS mount and on a local NVMe disk. All cold numbers come from Azure disks behind a host cache. A rotating disk may need a gate, but the `rotational` flag reads 1 on the Azure SCSI disks. Until then, `--no-spread` turns the scheduler off.
- Find why the first cold scan (round 0) of a new folder with 10,000 or 30,000 subfolders took a median of 2.07x and 1.25x of the time of main with the random order ([run 37990844034](https://github.com/OriginalMHV/minimenta/actions/runs/37990844034)), while rounds 1 to 5 were even.
- Sharded `first_link` mutex to skip repeated stats of hard links. Rated about 1.0x when cold. Source: internal notes.
- Small syscall ideas rated under 2%: a larger `RLIMIT_NOFILE`, io_uring for `openat` and `close` only, dedicated I/O workers with a deep prefetch window, and ext4 `inode_readahead_blks` (needs root). Source: internal notes.
- Re-baseline all Linux numbers on `ubuntu-26.04` before and after `ubuntu-latest` moves to it. The numbers here use `ubuntu-24.04` with kernel 6.17.0-1022-azure ([run 37904223270](https://github.com/OriginalMHV/minimenta/actions/runs/37904223270)). Source for the move: internal notes.

**macOS**

- Raw APFS read spike: as root with Full Disk Access, read block 0 of the data volume device and check one Fletcher-64 checksum. Drop the idea if the checksum fails. About 10 minutes of work. Source: internal notes.
- Cold measurements on bare-metal Apple silicon. The "cold" label is weak on the virtual runner, because cold `/System/Library` took 3.8 to 4.4 s and warm took 2.7 to 3.1 s ([run 37849524892](https://github.com/OriginalMHV/minimenta/actions/runs/37849524892)).
- A cold A/B run of the final [#23](https://github.com/OriginalMHV/minimenta/pull/23) code on a data-volume tree. The only cold point is the 0.73x of the first variant ([run 37850881974](https://github.com/OriginalMHV/minimenta/actions/runs/37850881974)).
- Explain why the total for `mm /` is still 16.7 GiB (7%) above the sum of `df` after [#31](https://github.com/OriginalMHV/minimenta/pull/31). Candidates that [#31](https://github.com/OriginalMHV/minimenta/pull/31) names: APFS clones count in full for each copy, and the cryptex disk images count twice.
- Refuse or warn on `d` and `D` for the `>` rows of firmlinked data folders. Trashing `/System/Volumes/Data/Users` removes the real home folders. `src/ui/browser.rs` has no `OTHER_FS` check. Source: review of [#28](https://github.com/OriginalMHV/minimenta/pull/28) (internal notes).
- Bump `VERSION` in `src/cache.rs` (it is still 4 on main at [`6e0eca0`](https://github.com/OriginalMHV/minimenta/commit/6e0eca0)) or store how firmlinks were handled. A cache of `/` written before [#31](https://github.com/OriginalMHV/minimenta/pull/31) keeps the doubled data volume until the 7-day limit or `r`. This matters only for builds from before the first release.
- Handle dataless files and File Provider folders. `src` has no handling, and the effect on `getattrlistbulk` is unverified. Source: internal notes.
- Switch off the autofs trigger policy (`IOPOL_TYPE_VFS_TRIGGER_RESOLVE`) during the scan. Source: internal notes.
- Test cache cases that the reviews did not cover: purged FSEvents history, `.fseventsd/no_log`, network volumes, symlinks swapped with directories, and changes during the replay. Source: internal notes.
- Run the macOS tests and clippy on an Intel Mac. [#5](https://github.com/OriginalMHV/minimenta/pull/5) notes that `BOOL` is `i8` on `x86_64-apple-darwin` and that clippy for that target was not run.
- Free the cache bytes earlier. The `Arc` keeps them alive until `incremental()` returns (follow-up of [#20](https://github.com/OriginalMHV/minimenta/pull/20)).
- Detect firmlinks with the `SF_FIRMLINK` flag in addition to the root file system rule. See the Dropped row above.

**Windows**

- USN journal cache for repeat scans, like the FSEvents cache on macOS. `FSCTL_READ_UNPRIVILEGED_USN_JOURNAL` might work without administrator rights. Two sources disagree on whether inaccessible names are withheld. USN records have no size field, so it can only find changed directories. Source: internal notes.
- Elevated relaunch for limited administrators, in the style of WinDirStat. It needs an owner decision and a manual test with a real limited token, because CI runs elevated. [#27](https://github.com/OriginalMHV/minimenta/pull/27) shipped a hint as the cheap alternative.
- `FSCTL_FILE_PREFETCH` with `FILE_PREFETCH_TYPE_FOR_DIRENUM`, to let the kernel batch directory metadata reads without administrator rights. Drop it if the gain is under 1.3x or a standard token gets `ACCESS_DENIED`. Source: internal notes.
- Test the claim that a standard user can read the MFT of a non-system NTFS volume. It needs no code change. CI cannot test it, because the runner is an administrator. Source: a forum report, internal notes.
- Sample random MFT records with `FSCTL_GET_NTFS_FILE_RECORD` to estimate the size of a folder. It would add about 100 to 300 ms of random reads (an estimate from internal notes). The random-path estimate on directory trees failed ([comment on #34](https://github.com/OriginalMHV/minimenta/pull/34#issuecomment-6081533783)), but this variant was never run.
- A setting `--mft=auto|always|never`. Only `--no-mft` exists.
- An adaptive MFT reader that starts with few or small reads and ramps up, or yields to the listing while the listing makes progress. Fixed block sizes, thread counts and priority hints failed, but no adaptive scheme was tried.
- A stored hint of the last scan time per folder to choose the MFT start on repeat scans. It cannot help the first cold scan.
- `NtQueryDirectoryFile` with a buffer above 64 KiB (WinDirStat uses 4 MiB), early dispatch of child directories from the first buffer, and narrower share modes. No run measured them.
- Measure the start policies on a slow-MFT runner (Xeon 8573C). Only main and [#34](https://github.com/OriginalMHV/minimenta/pull/34) ran there, and only on large folders. On `C:\Program Files` the median was 8.7 s for main and 11.9 s for [#34](https://github.com/OriginalMHV/minimenta/pull/34) ([run 37926570626](https://github.com/OriginalMHV/minimenta/actions/runs/37926570626)).
- Find out why dust needs 767 ms on the 51k tree where minimenta needs 32 ms ([run 37904223270](https://github.com/OriginalMHV/minimenta/actions/runs/37904223270)). The README says that we did not look into why.
- Check whether OneDrive placeholder folders carry the reparse attribute and are counted as links. This is unverified.
